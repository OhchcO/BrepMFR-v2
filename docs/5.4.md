# 5.4 基于 UG/NX 二次开发的识别系统与应用验证

前述章节分别给出了 B-rep 面级识别模型和实例关系推理方法。为使预测结果能够在 CAD 建模场景中定位和查看，本文基于 Siemens NX 2212 开发识别插件，将当前零件的 STEP 数据送入独立识别程序，再把输出的面级类别和特征实例对应到 NX 中的实际面对象。系统开发已覆盖输入获取、模型调用、跨内核面映射、结果着色和实例交互。本节说明各环节的实现及其验证范围。

## 5.4.1 UG/NX 识别系统总体架构

系统由 NXOpen C++ 插件、外部 Python 识别程序和 JSON 结果契约三部分构成。NX 插件负责读取当前 Work Part、定位原始 STEP 文件、启动识别进程、解析返回结果，并在 NX 图形窗口中显示识别实例。Python 程序负责 STEP 到图数据的转换、缓存校验、模型加载、面级语义与亲和关系预测，以及实例后处理。两部分运行在不同进程中，使 NX 的交互运行环境与 Open CASCADE、PyTorch 等计算依赖分开。

用户在 NX 中打开未经编辑的单实体 STEP 零件后加载插件。插件记录当前 Part、实体、源 STEP 路径和面数量，按配置启动 Python 进程；Python 将模型输出写为 JSON 1.1 结果，并附带 OCC/AAG 面签名。插件校验进程退出状态、JSON 字段与输入身份，再从当前 NX 实体提取面签名，完成面映射、着色和实例浏览。推理期间界面显示处理阶段与已用时间；程序返回后重新校验当前部件，避免在零件已切换或拓扑已改变时回写旧结果。系统不自动保存 NX 部件，颜色是否持久化由用户在 NX 中决定。

当前实现面向可追溯到原始 STEP 的单个精确实体。输入必须具有唯一的源 STEP，当前 Work Part 与识别期间的实体及面数量保持一致。此范围使 Python 使用的几何模型与 NX 窗口中的对象具有可检查的同源关系。**【待补文献：NXOpen、UFUN 与 Block Styler 的接口能力及版本约束，定稿时引用 Siemens NX 2212 官方开发文档。】**

## 5.4.2 UG/NX 面与图节点映射方法

模型输出的 `face_index` 是 OCC 构建属性邻接图时的面序号，NX 显示层使用的是会话内的 Face Tag。两者分别来自不同的几何内核和枚举过程，不能按整数值直接对应。本文将回写关系表示为“图节点序号 $\rightarrow$ OCC 面签名 $\rightarrow$ NX 面签名 $\rightarrow$ NX Face Tag”，仅在完整一一对应得到验证时执行面着色。

两侧首先采用同一实体包围盒进行位置和尺度归一化。设包围盒中心为 $\mathbf c$、最大轴向跨度为 $s>0$，三维点、长度和面积分别变换为 $(\mathbf p-\mathbf c)/s$、$l/s$ 和 $A/s^2$。这一处理使签名比较不直接依赖零件平移与长度单位。面签名包含曲面类型、边数、环数、邻接面数、面积、周长、重心和包围盒；平面、圆柱面、圆锥面、球面与圆环面另使用可取得的解析曲面参数。等价平面、轴线和轴向表达经过规范化后再比较。当前最终匹配评分不使用面内 UV 采样点。

映射先以曲面类型、边数、环数、邻接面数量及曲面参数存在性筛选候选，再按面积、周长、位置和解析参数的规范化误差构造候选代价。对所有面统一求解最小代价一一指派，随后将 OCC 邻接图按候选映射转换为 NX 面图，检查两侧邻接关系是否一致，并排除代价近似相同的歧义解。只有当每个 OCC 面均映射到唯一 NX 面、全部面均被覆盖且拓扑验证通过时，映射结果才可用于显示。图 5-X 可展示候选筛选、全局指派与拓扑复核的三阶段流程。**【图 5-X 待补：从现有实现绘制面映射流程图，并给出一个可追溯零件的映射日志。】**

这种完整性约束影响系统的失败行为：签名缺失、曲面属性不一致、全局指派无解或存在不可消除的对称歧义时，插件保留文字识别结果并停止面着色。它避免了“部分面已着色而其余面未匹配”的显示状态，也使后续实例浏览只接收已验证的面映射。

## 5.4.3 识别模型调用与 UG/NX 结果回写

插件通过本机配置确定 Python 解释器、推理脚本、模型检查点、输出目录、计算设备和实例亲和阈值，再调用 Windows `CreateProcessW` 启动独立进程。标准输出和错误信息写入运行日志，识别程序通过阶段消息报告转换、缓存读取、模型推理和结果写入状态。插件读取进程退出码与 `result.json` 的 `status`，只有两者及输入 STEP 信息一致时才继续处理。JSON 1.0 结果可用于文字展示；包含有效 `face_mapping` 的 JSON 1.1 才进入 NX 面映射与着色流程。

Python 端输出逐面的语义类别和概率、预测实例的成员面索引与置信度，并生成 OCC 面签名。NX 端完成上一节的一一映射后，将每个实例的 OCC 面索引转换为 NX Face Tag 集合，再为不同实例分配颜色索引。颜色计划在应用前检查面覆盖、实例 ID、重复面与颜色容量；当前颜色索引范围支持最多 216 个互异实例颜色，背景实体面保持原有颜色。插件用 NX 显示修改接口按颜色批量更新面，并在着色前建立撤销标记。若任何颜色组应用失败，程序回到撤销标记并显式恢复原颜色，使本次回写不保留部分着色结果。

完整着色成功后，插件打开基于 Block Styler 的特征实例浏览器。列表按实例 ID 展示特征类别、面数和置信度，每页最多显示 50 个实例。用户选中某一实例时，插件依据已验证的 Face Tag 集合临时高亮相应面；切换实例或关闭窗口时清除临时高亮，基础实例颜色仍保留。浏览器还可展示当前实例的 OCC/AAG 面序号和 NX Face Tag，完整文字结果可在 Listing Window 中查看。这个交互链路使面级模型输出、实例分组和 NX 图形对象保持可追踪的对应关系。

## 5.4.5 工业应用边界与失败模式分析

系统的可靠显示依赖输入可追溯、结果契约有效和跨内核映射唯一。源 STEP 无法唯一定位、当前部件包含多个实体或已修改拓扑时，插件在推理或回写前停止流程；Python 环境或检查点异常时，运行日志保留错误诊断。若识别本身成功但 JSON 仅为 1.0、面签名缺失或映射校验失败，系统仍可展示文字结果，同时禁止对未经确认的 NX 面着色。实例数超出颜色容量、颜色计划冲突及显示修改失败也进入不保留部分着色的安全路径。

跨内核映射的主要技术边界是几何与拓扑都难以区分的对称面，以及转换过程中无法保持一致的曲面参数或面划分。当前策略将这类对象判为歧义或匹配失败，并向用户呈现诊断，而不强行指定面身份。系统也尚未把经过 NX 编辑后的当前部件自动导出为新的 STEP，因而其输入范围限于未经修改、可追溯的单实体 STEP。上述限制涉及结果显示的正确性，应与第 5 章中模型对真实机匣的语义识别精度分开评价。

完成系统级验证时，应按同一检查表记录首次转换与缓存命中两种运行、成功与异常输入、面映射覆盖、实例着色数量、回写失败后的颜色状态，以及转换、推理、映射和显示各阶段耗时。**【系统验证统计待补：提供已完成的 NX 实测记录或测试报告后，在此填写独立零件数、成功率、映射覆盖率、各阶段时间和异常案例数量。】**
