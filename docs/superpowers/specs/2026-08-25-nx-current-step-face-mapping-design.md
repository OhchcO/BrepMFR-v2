# NX2212 当前 STEP 面映射与特征实例着色设计

## 1. 背景与目标

当前 NX2212 插件已经能够选择 STEP 文件、调用独立 Python CLI、读取识别 JSON，并在
NX 中显示文字结果。现有 JSON 中的 `face_index` 是 OCC/AAG 的 0-based 面编号，不能直接
当作 NX Face Tag 使用，因此当前插件不能安全地给识别面着色。

本阶段的目标是把正常使用流程收敛为：

1. 用户在 NX2212 中打开一个未经修改的单实体 STEP 文件；
2. 用户直接点击 BrepMFR 插件，不再选择文件；
3. 插件以当前 Work Part 对应的原始 STEP 路径调用现有 Python CLI；
4. Python 返回完整的识别结果和跨 CAD 内核面映射签名；
5. NX 将 OCC/AAG `face_index` 全局匹配到当前 Part 的 NX Face；
6. 完整映射通过后，按特征实例给对应面着色，同时保留现有文字结果。

系统边界继续保持不变：Python 负责 STEP 转 BIN、模型推理、后处理和 OCC 几何签名；
NX C++ 插件负责当前 Part 校验、进程编排、JSON 校验、NX 几何签名、面匹配和结果展示。
NX 进程不加载 Python、PyTorch 或 CUDA。

## 2. 固定范围

### 2.1 首版支持

- NX2212、VS2019/v142/x64；
- 当前 Work Part 来自现有 `.step` 或 `.stp` 文件；
- Part 中恰好包含一个实体 Body；
- STEP 打开后未进行几何修改，直接点击插件；
- JSON 1.0 继续显示原有文字结果；
- JSON 1.1 在文字结果之外提供面映射能力；
- 每个特征实例使用一种稳定颜色，同一实例内所有面颜色相同；
- 不属于识别实例的 stock 面保持原显示颜色；
- 识别或映射过程不自动保存 NX Part。

### 2.2 首版不支持

- 装配体、多实体、片体或收敛体；
- 打开 STEP 后发生的建模、删除、替换面或拓扑修改；
- 当前 Part 没有可用 STEP 源路径时自动导出 STEP；
- 继续保留正常流程中的 STEP 文件选择器；
- 把 OCC/AAG 面数组顺序直接当作 NX 面顺序；
- 映射不完整时进行部分着色；
- 特征点击选择、隐藏、图例面板、清除颜色命令；
- 自动保存、覆盖原 STEP 或持久化识别结果到模型属性；
- 常驻 Python 服务或在 NX 进程中嵌入 Python。

## 3. 用户流程与前置校验

插件启动后先获取 `Session::Parts()->Work()`，并执行以下校验：

1. Work Part 存在；
2. `BasePart::FullPath()` 非空，规范化后指向一个真实存在的文件；
3. 文件扩展名忽略大小写后为 `.step` 或 `.stp`；
4. 当前 Part 中恰好有一个实体 Body；
5. 能够枚举该 Body 的全部 Face。

任一条件不满足时，插件给出具体错误并停止，不启动 Python、不弹出文件选择器，也不猜测
源文件。NX2212 是否始终为中性格式导入后的 Work Part 保留原 STEP `FullPath()`，需要在
实现后的现场验收中确认。如果现场环境不保留该路径，则把“当前 Part 临时导出 STEP”作为
后续独立功能设计，不在本版本中暗中回退。

通过校验后，插件复用已有输出目录、进度窗口、Python 环境隔离和进程调用逻辑，只把 CLI
输入从文件选择器结果改为当前 Work Part 的 STEP 源路径。启动 Python 前记录 Work Part、
Body、源路径和面数量；着色前再次校验这些身份和数量没有变化，防止推理期间切换 Part 或
几何状态变化后仍把旧结果应用到新对象。

## 4. JSON 兼容与 1.1 契约

### 4.1 向后兼容

C++ 读取器同时接受 `schema_version` 为 `1.0` 和 `1.1`：

- `1.0`：严格按现有契约解析和显示文字结果，明确显示“映射不可用：JSON 1.0”，不着色；
- `1.1`：先独立校验原有识别核心，再校验新的 `face_mapping` 扩展；
- 未知主版本或未知次版本：拒绝使用，避免错误解释新语义。

JSON 1.1 保留 1.0 的 `input`、`cache`、`faces`、`instances`、计时和错误字段及其含义，原有
Listing Window 文字结果不得因为增加面映射而消失。

识别核心与映射扩展分层校验。只要识别核心有效，即可显示识别文字；映射扩展缺失、声明
不可用、损坏或无法与当前 NX Part 匹配时，只禁用着色并报告映射原因，不把已完成的识别
伪装成推理失败。

### 4.2 `face_mapping` 数据

成功的 JSON 1.1 必须包含 `face_mapping` 对象。其逻辑结构如下，字段名在实施阶段按此契约
固定，不允许从日志文本反向解析：

```json
{
  "schema_version": "1.1",
  "status": "success",
  "input": {
    "step_path": "D:/part.step",
    "face_count": 41
  },
  "faces": [],
  "instances": [],
  "face_mapping": {
    "contract_version": "1.0",
    "status": "ready",
    "normalization": {
      "kind": "aag_unit_box",
      "box_side": 1.0,
      "scale_rule": "2_over_longest_bbox_extent"
    },
    "faces": [
      {
        "face_index": 0,
        "surface_type": "plane",
        "area": 0.125,
        "perimeter": 1.5,
        "centroid": [0.1, -0.2, 0.3],
        "bounding_box": [-0.4, -0.5, 0.2, 0.6, 0.1, 0.3],
        "loop_count": 1,
        "edge_count": 4,
        "neighbor_count": 4,
        "surface_parameters": {},
        "sample_points": [[0.1, -0.2, 0.3], [0.2, -0.2, 0.3]]
      }
    ],
    "adjacency_edges": [[0, 1], [0, 4]]
  }
}
```

`face_mapping.status` 允许：

- `ready`：面签名和邻接图完整，可以尝试映射；
- `unavailable`：识别成功但签名无法产生，必须包含非空 `reason`，只能显示文字结果。

当状态为 `ready` 时：

- `faces` 数量必须等于 `input.face_count`；
- `face_index` 必须唯一、连续并与识别核心中的编号完全一致；
- 所有数值必须有限，数组维度固定；
- 邻接边必须使用有效面编号、无自环、无重复，并按端点升序规范化；
- `surface_parameters` 根据面型保存可跨内核比较的解析参数，例如平面、圆柱、圆锥、球面、
  圆环面的中心、轴、半径或角度；不适用的参数不得伪造；
- `sample_points` 是规范化坐标中的非空、确定性无序几何样本，只用于连续度量和歧义消解，
  不能单独决定映射。

错误 JSON 沿用原有错误语义；如果推理核心本身失败，则不存在“保留成功文字结果”的前提。

## 5. Python 端签名与缓存

### 5.1 与 AAG 完全一致的面身份

面签名必须从 `AAGExtractor` 已缩放后的同一 OCC shape/graph 中按 AAG 面顺序提取。这样
签名中的 `face_index` 天然就是模型输入和结果使用的 `face_index`，不再额外枚举一次原始
STEP 面，也不依赖另一个 OCC 遍历顺序。

签名提取是 JSON 1.1 的基础输出能力，不由 checkpoint 是否启用参数曲面编码等模型开关
决定。换用不同模型不能导致相同 STEP 的映射数据时有时无。

### 5.2 规范化坐标系

Python 和 NX 必须实现同一个 `aag_unit_box` 契约：

1. 在绝对坐标系中计算整个单实体的精确轴对齐包围盒；
2. 取包围盒中心作为平移中心；
3. 取三个方向跨度中的最长值 `L`；
4. 所有点先减去中心，再乘以 `2 / L`；
5. 面积乘以 `(2 / L)^2`，长度乘以 `2 / L`。

这与现有 `occwl.Solid.scale_to_unit_box(copy=True)` 的真实行为一致。禁止改用包围盒对角线、
各轴分别缩放或 NX 当前显示单位，否则两端签名将失去可比性。`L` 非正或非有限时映射数据
不可用。

方向向量不受平移和尺度影响，但必须单位化。对几何上无方向的轴线采用统一符号规则，例如
首个超过零容差的分量为正，以消除 OCC/NX 轴方向相反造成的假差异。

### 5.3 共享缓存与原子性

BIN 旁增加面签名 sidecar，例如：

```text
input.bin
input.face_signatures.json
input.bin.meta.json
```

缓存元数据记录签名契约版本、签名文件哈希以及生成实现指纹。命中缓存必须同时满足：

- STEP 内容指纹、转换实现、采样设置等现有 BIN 条件有效；
- sidecar 存在且 JSON 合法；
- sidecar 哈希、契约版本和面数量有效。

sidecar 缺失、损坏或版本不匹配时，视为转换缓存未完整命中，重新从 STEP 生成 BIN 与签名，
不能把旧 BIN 和新签名拼接。生成过程使用临时 BIN 和临时 sidecar，全部写完并校验后再原子
替换，最后写元数据；因此进程中断不会留下被误认为有效的混合缓存。

CLI 生成 JSON 1.1 时从本次转换对象或已验证 sidecar 填充 `face_mapping`，最终 `result.json`
仍保持自包含，NX 不直接读取缓存内部文件。

## 6. NX 端几何签名

NX 适配层对当前唯一实体的每个 Face 提取与 Python 相同语义的数据：

- 面型和解析曲面参数；
- 面积、周长、质心和精确包围盒；
- 环数、边数和相邻面数；
- 确定性几何样本；
- 由共享边建立的无向面邻接图。

实现优先使用 NXOpen 对象枚举和 UFUN 几何查询，例如 Body/Face/Edge 枚举、
`UF_MODL_ask_face_data`、`UF_MODL_ask_face_props` 和精确包围盒接口。NX API 只存在于薄适配层，
它把结果转换成不依赖 NX 头文件的普通 C++ `FaceSignature` 和 `FaceGraph` 数据结构。

适配层使用与第 5.2 节完全相同的 Body 级变换规范化全部长度、面积、位置、解析参数和样本。
不得对每个面单独归一化。

本功能依赖 NX2212 中可用的实体几何查询与显示修改能力；构建环境和运行许可证不足时，应
报告 NX API 错误，而不是退化为面数组顺序映射。

## 7. 全局一对一面映射

映射器是独立于 NX API 和 JSON 库的纯 C++ 模块，输入为 OCC 签名图和 NX 签名图，输出为
`face_index -> NX Face identity` 或结构化失败原因。

### 7.1 快速拒绝

首先验证：

- 两端面数相同；
- 面型直方图和基础拓扑统计可兼容；
- 所有签名和邻接引用有效；
- 当前 NX Body 能够构成完整邻接图。

任一验证失败立即终止映射。

### 7.2 候选集

每个 OCC 面只保留满足离散条件的 NX 候选面：

- 规范化后的曲面类型兼容；
- 边数相同；
- 环数相同；
- 相邻面数量相同；
- 必需解析参数存在且类型相容。

任一 OCC 面候选集为空即失败。首版容差是经黄金样例验证后固化的内部契约，不暴露为普通
用户配置，避免现场任意放宽后产生错误着色。

### 7.3 连续代价与全局分配

对候选对计算加权代价，至少包括：

- 规范化面积和周长相对误差；
- 质心、包围盒和解析曲面位置误差；
- 半径、角度等解析参数误差；
- 规范化无序样本集的双向几何距离。

轴和法向比较采用前述符号规范或方向无关距离。随后在全部候选上求最小总代价的一对一分配，
不能逐面贪心匹配，也不能依赖 `GetFaces()` 的返回顺序。

### 7.4 拓扑验证与歧义处理

得到全局分配后，将 OCC 邻接图映射到 NX face identity，并要求两端邻接关系完全一致。
同时检查每个匹配误差、最大误差和总代价均在固定阈值内。

如果出现以下任一情况，映射整体失败：

- 无完整一对一解；
- 连续误差超限；
- 邻接图不一致；
- 存在多个代价近似相同且无法由样本和拓扑消解的解；
- 任一面或实例引用无法转换到 NX Face。

确定性排序只能保证相同输入得到相同结果，不能用来掩盖真实几何歧义。首版采取 fail-closed
策略：宁可保留文字结果而不着色，也不冒险把特征颜色涂到错误面上。

## 8. 着色、回滚与显示

实例按 `instance_id` 升序使用固定的 NX 颜色调色板。颜色只由实例编号决定，因此同一识别
结果在缓存未命中和命中两次运行中保持一致；同一实例的所有 NX Face 使用同一种颜色，
不同实例使用不同颜色，stock 面不加入显示修改集合。着色前必须确认实例数量不超过调色板
可提供的互异颜色数量；超出时保留文字结果并拒绝着色，不能循环复用颜色破坏实例区分。

着色必须晚于以下所有步骤：识别核心校验、映射扩展校验、完整一对一匹配、拓扑验证以及
所有实例引用展开。插件先保存本次将修改的 Face 原显示颜色，并建立 NX undo mark，再统一
应用显示修改。如果任一应用或刷新失败，恢复全部已修改面的原颜色并报告错误，禁止留下
半着色状态。

插件不会调用保存。显示属性可能使当前 Part 呈现为已修改状态，是否保存完全由用户决定。
首版针对“打开后未修改、直接识别”的流程；用同一配置重复识别是幂等的，但不提供通用的
“恢复任意历史着色”命令。

## 9. 结果展示与错误行为

Listing Window 始终保留现有内容：

- 当前 STEP 路径和 `result.json` 路径；
- OCC/AAG 面数、缓存状态和各阶段计时；
- 每个实例的特征名、置信度和 OCC/AAG `face_index`。

映射成功后追加：

- `Mapped faces: 41/41`；
- 映射状态、最大匹配误差和映射用时；
- 每个实例对应的 NX Face Tag 和颜色编号。

完成消息框同时显示识别实例数、映射面数、已着色实例数和总用时。

映射不可用或失败时：

- 已验证的识别文字照常输出；
- 明确提示“识别成功，但面映射失败”；
- Listing Window 输出失败阶段、具体原因、候选或误差摘要；
- 不改变任何 Face 颜色；
- 不把 OCC `face_index` 显示成 NX Face Tag。

当前 Part 校验失败、Python 进程失败或识别核心 JSON 无效，继续沿用现有失败路径，不进入
面映射和着色阶段。

## 10. 代码边界

预计新增或调整的职责如下，具体文件拆分在后续实施计划中确定：

- Python `face_signature`：从 AAG 已缩放 shape 提取跨内核签名和邻接图；
- Python conversion/cache/result：原子维护 sidecar，输出 JSON 1.1；
- C++ `result_reader`：分层解析 1.0/1.1 核心结果和映射扩展；
- C++ `face_signature`：纯数据结构、单位和规范化工具；
- C++ `face_matcher`：候选、代价、全局分配、拓扑验证和诊断；
- NX adapter：当前 Work Part、唯一 Body、NX 签名、Face identity 和显示颜色；
- plugin runtime：从当前 Part 输入到推理、映射、原子着色和文字展示的编排；
- result formatter：兼容旧文字结果并增加映射诊断。

纯算法模块不得 include NXOpen 头文件。这样可以在不启动 NX 的情况下覆盖映射算法、JSON
兼容、失败封闭和颜色计划；NX 现场测试只承担 API 适配与真实导入行为验证。

## 11. 测试与验收

### 11.1 Python 自动化

- JSON 1.0 现有黄金结果和回归测试保持通过；
- JSON 1.1 `ready`、`unavailable` 和错误文档校验；
- 签名面编号与 AAG/推理 `face_index` 完全对齐；
- STEP 平移、单位尺度变化后，规范化签名在容差内一致；
- sidecar 首次生成、有效复用、缺失、损坏、版本变化和哈希不匹配；
- BIN、sidecar 和元数据原子提交，中断后不产生假命中；
- 相同输入的签名和邻接输出确定性一致。

### 11.2 原生 C++ 自动化

- JSON 1.0 只显示文字且不产生颜色计划；
- JSON 1.1 核心有效但映射不可用或无效时仍保留文字结果；
- 面数组随机置换后仍得到同一全局映射；
- 平移、尺度和允许数值扰动不改变映射；
- 重复几何、缺面、多面、错误面型、断裂邻接和歧义解均整体失败；
- 任一面失败时颜色计划为空，不允许部分着色；
- 固定实例调色板在重复运行中稳定；
- Python 缓存未命中和命中结果生成相同的 NX 映射与颜色计划；
- 进度、文字格式和现有进程错误测试继续通过。

### 11.3 仓库与构建验证

- 完整 `pytest` 回归通过；
- `BrepMFRNx2212RuntimeTests` Release/x64/v142 通过；
- `BrepMFRNx2212.dll` Release/x64/v142 构建成功；
- DLL 继续正确导出 `ufusr` 和 `ufusr_ask_unload`；
- 项目文件包含新增源文件且不引入在线运行依赖。

### 11.4 NX2212 黄金样例

使用现有 `20221121_154647_0.step`：

1. 在 NX2212 中直接打开 STEP，不做修改；
2. 点击插件，不出现 STEP 文件选择器；
3. 首次运行完成推理，映射必须为 `41/41`；
4. 9 个识别实例分别着色，同一实例颜色一致，stock 面保持原色；
5. Listing Window 同时包含原文字结果、NX Face Tag、映射误差和计时；
6. 再次运行命中 BIN/签名缓存，识别、映射和颜色与首次一致；
7. 面映射阶段目标用时小于 1 秒，不破坏已达到的 Python 推理性能；
8. 插件不自动保存；关闭或保存行为由用户决定；
9. 人工制造 JSON 1.0、签名损坏和面数不一致，确认文字结果保留且颜色零修改。

## 12. 风险与后续边界

- NX 导入 STEP 后是否保留原 STEP `FullPath()` 是首个现场门槛，必须实测，不能靠猜测；
- 不同 CAD 内核对自由曲面、修剪边界和数值积分可能存在差异，容差只能由黄金样例和负例共同
  标定，不能只为通过单个样例持续放宽；
- 完全对称且几何、拓扑均不可区分的面可能没有唯一跨内核身份，首版应拒绝着色；
- 若以后允许用户修改 Part，必须增加几何变更检测或改为导出当前 NX 几何，不能继续复用
  原始 STEP 路径；
- 多实体、装配体、颜色图例、交互选择、恢复颜色和当前 Part 自动导出均需要独立设计，不在
  本阶段顺带实现。

本设计的成功标准不是“在一个样例上看起来颜色正确”，而是：只有完整、唯一、经几何和
拓扑共同验证的映射才能触发原子着色；其他情况全部保留可靠文字结果并安全失败。
